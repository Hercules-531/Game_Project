## Scope and assumptions submitted for approval

The full game follows the GDD: a finite northward campaign, remote machines as the normal mode of surface access, recovery instead of an immediate game-over when the fleet is stranded, and excavation that hardens already claimed territory. Terraforming, rival bunkers and hostile enemy droids are excluded because they are parked or undecided. Human artifact implantation is also undecided and is not silently added. No dialogue or narrative beats will be invented; Dialogic becomes relevant only if such content is specified.

Proposed engineering choices: GDScript, modular scenes, data resources for tunable definitions, and separate simulation state from terminals and camera presentation. Simulation continues while the operator changes stations; pause deliberately freezes it. Every persistent system extends the save schema as it is added. Large chassis still require external power support; their normal control restrictions remain a design gate below.

Proposed visual baseline: 320x240 internal rendering at 4:3, nearest integer enlargement with letterboxing, 32–64px imported surface textures, nearest sampling, no mipmaps, vertex snapping, affine mapping, and compositor-based dithering/chromatic aberration/grain. The fixed resolution is a proposal, not specified by the GDD. The 15 FPS restriction applies to Tier 1 optical feeds, not player movement or the whole simulation. Live screen/UI rendering is kept distinct from imported surface art.

Proposed basic bunker controls: WASD and mouse look, E to use, Escape to pause/release the current interaction as appropriate. No jump, sprint, crouch, head bob or camera shake will be added without a design decision. Movement speed, eye height, FOV and effect strengths will be exposed for review rather than described as GDD facts.

M01–M12 establish the technical and bunker foundation. M13–M26 build and verify the first complete remote-salvage/recovery loop. The remaining milestones extend that loop into the full campaign. This order does not remove later requirements or represent a claim that a 40-hour campaign is already specified.

## Verification and commit rule for every milestone

1. Implement only the current approved milestone and its necessary integration. Inspect the diff before committing. Do not move ahead until its acceptance checks pass.
2. Refresh the editor filesystem as needed; use project_run(mode="custom", scene=...) for the milestone scene or mode="main" for integrated flow. Confirm live game status, not just a successful tool return.
3. Exercise the behavior using MCP game evaluation/input and observe measurable before/after state. Use GUT for gameplay logic and boundary cases. Do not substitute tests that merely mirror the code for meaningful outcomes.
4. Capture editor_screenshot(source="game") for visible behavior and inspect it. Reject stale frames as evidence. Rendering milestones always need a real rendered frame; headless startup cannot prove PS1 appearance.
5. When a graphical check is unavailable, use a headless behavior scenario with explicit assertions, exit status and logs. Record the limitation; leave visual acceptance open until a screenshot/user review resolves it.
6. Save concise evidence in docs/verification/MNN.md and relevant screenshots under docs/verification/MNN/. Record expected/observed behavior, tool results, test outcomes and unresolved issues. Do not commit generated import caches or save-game files.
7. Commit that working milestone only, using the concrete messages below. Never push automatically. Report outcome, evidence and commit before moving to the next milestone; pause for any scheduled review gate.

The file lists below are planned new or changed paths relative to the project root. Every milestone also updates docs/verification/MNN.md and docs/BUILD_LOG.md. Main-scene wiring and save integration are named where relevant. Imported Godot .uid sidecars accompany their resources. Exact selected texture .import sidecars are recorded by source path before each art change; no wildcard grants permission to modify unrelated assets.

## Review points and limits

- Review the measured bunker layout before M05, the rendered bunker after M09, the complete first salvage/recovery loop after M26, the threat/expansion loop after M33, and excavation/rail/breach behavior after M40.
- Each lettered submilestone has its own acceptance evidence and commit. The required subdivisions above take precedence over the larger group rows. Final band count and authored content names remain gated on the GDD's unresolved scope.
- Missing external export templates or required addon files are reported and resolved before calling a milestone complete. Tooling success is verified, not inferred from configuration.
- Screenshots establish rendered behavior and appearance; state assertions establish mechanics; human playtesting establishes readability, tension, and pacing. None substitutes for all three.
- The first action after plan approval is M01 only. No gameplay code, shader, scene, import setting, addon or Git configuration has been changed during planning.
